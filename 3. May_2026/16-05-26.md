# Intuition
The presence of duplicates introduces a nasty edge case to the standard binary search approach used in the previous "Find Minimum in Rotated Sorted Array" problem. 

In a standard rotated array without duplicates, comparing the middle element to the rightmost element always gives you a clear direction. But consider these two arrays:
1. `[1, 0, 1, 1, 1]` 
2. `[1, 1, 1, 0, 1]`

In both cases, `nums[mid]` is `1` and `nums[right]` is `1`. Based purely on `nums[mid] == nums[right]`, you have absolutely no mathematical way of knowing whether the minimum (the `0`) is in the left half or the right half.

To solve this, we have to compromise. If `nums[mid] == nums[right]`, we can't eliminate half the array. However, we *can* safely eliminate the `right` element by doing `right -= 1`. Why? Because even if the minimum value happens to be `nums[right]`, we know that exact same value exists at `nums[mid]`, so we aren't losing the minimum from our search space.

# Approach
1. **Initialize Pointers:** Set `left = 0` and `right = len(nums) - 1`.
2. **Binary Search Loop:** Run a `while left < right` loop.
3. **Calculate Midpoint:** Find `mid = left + (right - left) // 2`.
4. **Compare and Shift:**
    * If `nums[mid] > nums[right]`: The minimum is strictly to the right. Set `left = mid + 1`.
    * If `nums[mid] < nums[right]`: The right half is perfectly sorted, so the minimum is at `mid` or to its left. Set `right = mid`.
    * **The Duplicate Case:** If `nums[mid] == nums[right]`, we are blind. Safely shrink the search space by dropping the rightmost element. Set `right -= 1`.
5. **Return:** When the loop terminates, `left` will point to the minimum element. Return `nums[left]`.

# Follow-Up: Runtime Complexity
Yes, the duplicates absolutely affect the runtime complexity. 
* **How:** The worst-case time complexity degrades from $\mathcal{O}(\log n)$ to $\mathcal{O}(n)$.
* **Why:** If the array consists of all identical elements (e.g., `[2, 2, 2, 2, 2]`), `nums[mid]` will always equal `nums[right]`. Our algorithm will be forced to decrement `right` by exactly `1` on every single iteration, reducing the search space linearly rather than logarithmically.

# Complexity
- **Time complexity:**
  - Average Case: $\mathcal{O}(\log n)$
  - Worst Case: $\mathcal{O}(n)$
- **Space complexity:** $\mathcal{O}(1)$ 
  We only use pointers, requiring constant extra memory.

class Solution:
    def findMin(self, nums: list[int]) -> int:
        left, right = 0, len(nums) - 1
        
        while left < right:
            mid = left + (right - left) // 2
            
            if nums[mid] > nums[right]:
                # Minimum must be in the right half
                left = mid + 1
            elif nums[mid] < nums[right]:
                # Minimum is in the left half, or is mid itself
                right = mid
            else:
                # nums[mid] == nums[right], we can't be sure which half to pick.
                # But we can safely discard the rightmost element.
                right -= 1
                
        return nums[left]
